代码质量问题已经解决，但业务门槛问题尚未解决。

2026年5月9日下午4点32分左右，Claude完成了一个看起来很完整的Electron IPC补丁。所有47项测试都通过了。但Mac摄像头仍然无法切换。

处理程序语法正确：它是一个 `subscribe` 回调函数，在收到空快照时会清除通话记录缓存。问题不在于代码本身，而在于空快照的*含义*。NECallKit 的适配器会在其初始化阶段发出一个空快照——**在任何业务清除操作发生之前**。“适配器尚未初始化”和“数据已清除”在渲染器中看起来完全相同；只有团队内部的规范区分了它们。

这并非更高级的LLM（语言学习模型）就能发现的bug。代码在LLM所掌握的规范下是正确的，但在NECallKit团队独有的规范下是错误的。（在内部测试语料库中记录为B074：`dogfood-necallkit-hn-essay.md:3237`。）

## 为什么这很重要

多年来，人工智能工具一直在蚕食代码质量。最初是格式化工具和代码检查工具，然后是类型检查器和代码审查机器人。现在，Claude、Codex 和 Copilot 等工具能够生成完整的补丁，并通过审查，顺利合并。每一层都曾是工程师们的一道护城河，直到这道护城河变成了商品。

那些尚未崩塌——而且我认为也不会以同样方式崩塌——的部分，是“这段代码应该做什么”中并不存在于代码本身的部分。**项目特定的业务语义**。阈值。生命周期不变式。领域约定。自 2024 年以来就存在于 Slack 讨论串中的协议规则。一位工程师构思但从未记录下来的拆卸流程。每当有人问“等等，这在我们的系统中到底*意味着什么*？”时，这些知识都会被重新推导出来。

称之为**L1：代码正确，业务错误**。这是LLM在实际项目中运行时常见的系统性故障模式，就我自己的项目而言，这是我们目前仍然面临的最昂贵的bug类型。这并非因为LLM本身存在缺陷，而是因为LLM被问及了一些项目从未记录过的问题。

实验

NECallKit 是一个真正的 Electron + 原生视频通话 SDK——支持多平台，提供原生 IPC 桥接，兼容 macOS、Windows 和 Linux，并支持 Java、JS 和 C++ 并行开发。它并非玩具。在四周的时间里（2026 年 4 月 25 日至 2026 年 5 月 13 日），我进行了一项配对实验：将项目中的所有 bug、决策和提交的查询都路由到一个由 AI 维护的 wiki 中，并测量哪些因素会产生影响。

该维基工具是 **Kata**（历时六周，版本从 v1.4 升级到 v1.11），基于 Karpathy 的 LLM-Wiki 原则构建。其流程很简单：人工整理资源，AI 代理读取、总结、交叉链接并归档。页面会不断编译——信息综合已内置，矛盾之处会被标记，查询会被归档为新页面。该维基并非检索工具；它是**编译后的知识库**，会随着项目的推进而保持更新。在 200 多个会话中，Claude Code 和 Codex CLI 轮流担任维护代理；我负责整理。

我最初的假设很简单。维基百科可以帮助进行交叉引用——LLM学员已经熟悉Electron、Node和标准Web。或许它还能加快我中途设置的第二台机器的上手速度。

我首先要写的其实不是交叉引用，而是这篇文章。

冲突

B074并非个例。在三周时间里，我寄出了三个形状相同的虫子：

- **B066** — `normalize()` 函数在执行过程中会清除 `cleared` 字段。协议将 *absent* 和 *explicitly-undefined* 视为不同的信号（一个表示“不更新”，另一个表示“主动清除”）。LLM 对此并不知情。它看到了两个假值，并将它们折叠了。

- **B070** — Electron 渲染器直接调用了 `sdk.setCallConfig`。在 Windows 系统上可以正常工作；但在 Mac 系统上，渲染器的 `sdk` 引用为空，因为原生 SDK 位于主进程中，而不是渲染器进程中。LLM 前面有可正常运行的 Windows 代码，它复制了该模式，并在 Mac 系统上执行了一个静默的空操作。所有测试都通过了。没有程序崩溃。只是静音开关没有生效。

- **B074** — 引言中提到的适配器快照生命周期案例。

（集群来源：`dogfood-necallkit-hn-essay.md:3231-3251`。）

![L1 / L2 失败分类](../assets/essay/V2-l1-l2-failure-taxonomy.svg)

L1（左列）是我在本文中所指的认知家族。L2（右列——会话内注意力偏差、跨会话模式盲视、会话边界丢失）是另一篇文章的内容；暂时忽略它。

B066/B070/B074 中的每一个都**符合 LLM 使用的通用 Electron 规范，但不符合团队内部使用的 NECallKit 规范**。这三次会议，三位不同的客服人员，间隔三周。**没有一次会议将其视为一个整体。**该类在结构上对聊天相关的智能来说是不可见的——每次错误修复都是局部性的；模式识别需要跳出对话进行分析。每次会议都只是对代码库进行了改进，而该类本身则完全不可见。

维基百科就存在于这种外部环境中。它并非按需检索；它是会话之间存在的一种载体，下一个代理在写入一行内容之前会先读取它。

## 维基百科如何汇总差距

我用狗粮测量了一个数字：在五个拐点处，编译后的维基中的图边数。

| 事件 | 页数 | 边数 | Δ |

|---|---:|---:|---|

| t0 — 导入功能档案 | 56 | 0 | 基线 |

| t1 — 提交 2 个维护者决策查询 | 61 | 26 | +26（来自 5 页） |

| t2 — 导入项目运行环境 | 69 | 68 | +42（来自 8 页） |

| **t3 — 提交运行边界查询** | **70** | **85** | **+17（来自 1 页）** |

| t4 — 经验种子 + 预检查询 | 77 | 134 | +49（来自 7 页） |

（来源：`dogfood-necallkit-hn-brief.md:40-47`。）

![边缘进展——合成与导入](../assets/essay/V1-wiki-compounding.svg)

t3 是关键所在。**一个提交的查询，一个新页面，+17 个边。**导入内容平均每个页面大约增加 5 个边。而一个提交的维护者决策查询则会增加 17 个边。wiki 不会在你加载时增长；它会在有人提出维护者决策问题时增长，答案会*连同指向现有页面的交叉链接*一起返回到 wiki 中。

维护者决策查询具有特定的结构。它不是“这个函数是做什么的”——那是规范式的，LLM 已经知道了。而是“NECallKit 在适配器生命周期周围的 mac IPC 拓扑结构是什么？我们的哪些模块依赖于这个契约？” AI 会将答案写成一个 wiki 页面，并交叉引用每个受影响的模块、同一区域内的每个先前 bug 以及每个保护边界的测试。该页面成为一个中心枢纽。后续的会话在接触代码之前都会先查看该页面。

我根据正确性、实用性和保留率三个维度对四个已提交的查询进行了评估。所有四个查询在正确性和保留率方面都获得了满分5分；四个查询中有两个在实用性方面获得了满分（`dogfood-necallkit-query-acceptance.md:48-82`）。维护者采用的标准是**领域正确性**，而不是语法合理性。这些查询之所以有用，是因为它们编码了LLM*无法*从代码中推断出的规范部分——它们编码了团队对事物运作方式的持续判断。

吃到一半的时候，我在日志里写下了一句话，这句话后来成了本文的论点：

“在代码编写工作开始之前，维基应该编译一个特定领域的预检查询。”

（`dogfood-necallkit-hn-essay.md:2526-2527`。）这就是“一页+17”的意义所在。维基百科不是参考资料，而是**商业语义汇编**。

## 课程

三个字，值得引用：**代码正确，商业错误**。

概括来说：人工智能工具非常擅长处理**规范化**的知识——这类知识已经写入编程语言、框架、公共 API 文档、标准库以及 GitHub 已经磨合了十年的约定中。模型知道 JavaScript 中的 `subscribe` 函数是什么样子；它知道 Electron 渲染器可以访问哪些内容，不能访问哪些内容；它知道 `null` 引用的作用。这部分已经得到解决，而且未来还会得到更多解决。

模型所不了解的是**未定义规范**的部分。那些局部性的真相。比如*你的*SDK的MAC地址与主进程的划分。在三个生命周期阶段分别代表三种不同含义的协议字段。还有你之前的工程师在客户服务中断后确定的3.5秒超时时间。这些信息都不在编程语言中，也不在框架中。它们存在于三位工程师的脑海中，并且每次有人提出错误的问题时，它们都会被重新推导出来。

经济预测虽然令人不安，但却直截了当：随着代码质量工作不断落入人工智能手中，资深工程师的长期贡献将从“编写代码”转向“编译业务规范”。工作内容也从“生成产品”转变为“制定产品必须遵循的规则”。维基百科就是这种编译的一种形式。未来还会有其他形式——模式库、契约测试套件、决策日志、机器可读的不变式声明等等。你可以选择其中一种，或者自己创造一种。

这并非人工智能功能薄弱的故事。人工智能的强大之处在于它完全符合规范。问题在于，我们从未将非语言特性部分写入规范，因为在过去的十五年里，我们并不觉得这很紧迫。但现在情况不同了。

提升的阶梯是选择一个用于编译业务语义的 Kata——采用一个，将其调整以适应你的项目，然后超越其形式。Kata（本文描述的工作流程）就是这样一种阶梯；你的项目可能看起来有所不同。重点不在于 wiki，而在于拥有一个编译好的业务规范层。

接下来会发生什么？

**存在未解决的问题。** 我还没有进行冷基线对比——同样的问题，同样的代理，没有维基百科。我认为复合效应的表述很恰当，但在我断言其有效性之前，我需要进行测试。该问题已在内部测试日志中标记（`dogfood-necallkit-hn-essay.md:996-999`）；下一个实验。

**范围说明**。本文探讨的是 Kata 的**第一阶段**——人工智能辅助工程。Kata 的核心是一个基于 Karpathy 底层架构的自演化维基，具备自动生成梦境的功能；第一阶段将该核心应用于项目记忆。**第二阶段**——团队规范编写 + 争议解决（形成一个自闭循环）——目前已完成设计，尚未实现。本文的综合论点具有普遍性，但具体步骤并非如此。

**下一个实验。** v1.11 `wiki-session-ingest`（PRD 草稿 v2：`docs/PRD-v1.11-session-ingest.md`）——该技能读取当前 CLI 会话，提取知识点，并允许用户多选要归档的知识点。它是针对另一种故障模式（L2——知识产生于对话，在会话边界处消亡）的结构性解决方案，下一篇文章将对此进行探讨。

你不需要使用 Kata 来完成这项工作。为你的团队选择一个 Kata——可以 fork 我们的 Kata，也可以自己编写一个，或者完全采用另一个 Kata。关键不在于工具本身，而在于它所包含的层面。
