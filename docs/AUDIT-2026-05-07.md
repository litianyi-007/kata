## 1. 产品视角 — 叙事不一致与承诺/实现错位

### 1.1 【🔴 HIGH】README & 标准 prompt 仍在示范一个**已删除并会被拒绝执行**的接口

`PLUGINS.md` 在 v1.4 把 `command_template:` 从外部插件接口里剥掉了
(原因: 命令注入风险)，`external_plugin_run.py` 检测到 `command_template`
直接 return code 3。但是:

- `README.md` 第 504-512 行仍把 `command_template:` 当作示例配置教用户写
- `SKILL.md` (standalone prompt, 根目录) 第 77 行: "Each plugin has a
  `command_template`"
- `plugin/skills/wiki-query/SKILL.md` 第 195 行步骤 ②a:
  "Render the plugin's `command_template`…"

**后果:** 任何按 README/standalone prompt 设置外部插件的用户会得到 100%
失败的配置；agent 在 `wiki-query` 时也会按 SKILL.md 描述去找一个不存在的字段。
这是把安全修复半吊子地落地的典型形态。

### 1.2 【🔴 HIGH】Skill 索引在三个文档中给出三套不同的数字

- `plugin.json` / `marketplace.json`: 12 skills (init, import, ingest,
  search, graph, tier, digest, query, lint, **config, dream, watch**)
- `README.md` "Skills" 表格 (197-208 行): 9 skills (缺 config / dream / watch)
- `SKILL.md` 自动生成表 (104-119 行): 12 (正确)，但同一文件 121-365 行的
  "Skills" prose 章节只展开了 9 个 (没有 dream / watch / config 详述)

**后果:** 复制 `SKILL.md` 当 standalone prompt 的人看不到 dream/watch/config，
等于这三个 skill 在 "any LLM" 模式下不存在。这正是 README 第 132 行宣传的那条
三步路径——目前的产物是残缺的。

### 1.3 【🟠 MEDIUM】wiki-init 不实现 wiki-dream 文档承诺的「初始化时写 cron」

- `wiki-dream/SKILL.md` 第 119 行: "The wiki-init skill writes this cron
  line during interactive setup if the user enables dreaming."
- `wiki-init/SKILL.md` 全部步骤都不问 dreaming，也不写任何调度行
- `wiki_init.py --template market_research` 把 `dreaming:` block 写进 SCHEMA
  但**不**生成 cron / `/schedule` 命令

**后果:** 用户期待 "init 一次自动起飞"，实际还要看 `dogfood-guide-v1.6.md`
找到那行 `claude /schedule`。这是 v1.6 dogfood 4 周观察期里最容易让用户
不开始第一周的摩擦点——而 dogfood 没启动 = 不能 tune 阈值 = 不能进 v1.8。

### 1.4 【🟠 MEDIUM】Dogfood 4 周观察期可能根本没真启动

- `docs/dogfood-v1.6.md` 第 16-26 行的 setup 表格里五个核心字段全是
  `_<fill in>_` 占位
- 对比 currentDate 2026-05-07 与 PRD 的 4 周窗口要求: 如果连日志都没起头，
  week-4 retrospective 就没有可比数据

**建议:** 把 dogfood-v1.6.md 当成阻塞性 issue，要么填 setup、要么承认延期。

### 1.5 【🟠 MEDIUM】skill 之间的边界交错让用户不知道走哪条

- `wiki-tier` 写 `tier_override`，`wiki-config --set` 写 SCHEMA tier 阈值，
  `wiki-dream --apply` 也写 `tier_override` 还附带写两条
  `tier_override_reason` / `tier_override_set_at`——三个 skill 同时往一个字段
  塞东西，**写入语义不一致**: tier 不写额外字段，dream 写。lint 没有任何 check
  验证三方的产物兼容。
- `wiki-watch --drain` 调 `wiki-ingest`，`wiki-import` 也走类 ingest 风格，
  但二者参数 / 提示路径完全不重叠。重复 surface area。

### 1.6 【🟡 LOW】`wiki-config` v1.6 限制是诚实的，但容易被用户撞上

`wiki-config` 自己声明 "edits existing scalars only / no list-index /
no multi-key"，但 SCHEMA.md 里 `custom_dimensions[*].required` 之类正是
用户最想批量调的东西。当用户撞上 "could not locate the line" 的 fallback
错误时，建议直接打印目标 block 当前的原文 + 一个 `# TODO change me here`
锚点，比纯错误信息有用得多。

## 2. 研发视角 — 实现层 gap 与潜在 bug

### 2.1 【🔴 HIGH】多项目 watcher 共用一个 PID 文件 — 跨项目互斥 bug

`plugin/scripts/wiki_watch.py:39-41`:

```python
PID_DIR = Path.home() / ".kata"
PID_FILE_NAME = "watcher.pid"
```

PID 文件路径**与 `--wiki` 无关**。v1.7.2 同时鼓励
`~/.llm-wiki/{necall, rtc, common}` 多项目布局——用户在 `necall` 跑
`--start`，再去 `rtc` 跑 `--start`，第二条 `is_pid_alive(existing[0])`
命中，第二个项目永远起不来。`status` / `stop` 也只看一个 PID，会报告错的项目。
**v1.7.2 的多项目卖点直接被这个守护进程实现破坏。**

**修复:** PID 文件名加项目 slug，例如 `watcher-{slug}.pid`；status / stop
按 `--wiki` 找对应 pid。

### 2.2 【🔴 HIGH】`wiki-search` SKILL.md 宣称的排序与脚本实际不一致

SKILL.md (line 196 / search_naive.py 文档注释) 写的排序:
"title > **hub centrality** > content frequency > recency"。

脚本 `search_naive.py:95-105` 实际排序:
`(-title_match, -tag_match, -body_match, _negstr(updated), p.path)`。
**Hub centrality 完全没用上** (`grep hub_score search_naive.py` 0 命中)。

**后果:** 三个 wiki ingestion / query skill 都依赖 search 找入口页，但用户读到的
"排序逻辑"是错的；中心节点不会被优先返回。

### 2.3 【🟠 MEDIUM】`wiki-lint` 的 stale 检查兑现的不是 SKILL.md 描述的语义

SKILL.md `wiki-lint` check 5: "Pages whose `updated` date is older than
**any source that mentions the same entities**."

`lint_naive.py:118-138` 实现: 仅 `updated < today - stale_days` 的纯阈值。
**没有比较"提到相同 entity 的更新源"** 这个语义层。

要么把承诺收回 (诚实地说 LLM 那部分仍在 prompt 里)，要么真把 entity-aware
staleness 实现进去。

### 2.4 【🟠 MEDIUM】`digest.py` 的 inventory 不计 `created` 字段

SKILL.md 步骤 ③: "New pages since `--since` date (compare against `created`
frontmatter)"。

`digest.py:68-82` 只用 `updated`，不读 `created`。"新建" 和 "更新"
被合并成一个。

### 2.5 【🟠 MEDIUM】`wiki_dream._apply_promote` 直接做行级 frontmatter 改写

`wiki_dream.py:347-367` 用纯 splitlines + append 三行
(`tier_override`, `tier_override_reason`, `tier_override_set_at`)。问题:

- 不去重旧的 `tier_override_reason` / `tier_override_set_at`，再 apply 就会
  **叠加**两条相同 key
- 同一 page 反复 apply (例如人工先 pin 再 dream)，frontmatter 里出现重复 key
- 没有 lint 检查 `tier_override_reason` 是否过时

### 2.6 【🟠 MEDIUM】自定义 YAML 解析器是中长期负债

`wiki_lib._parse_yaml_block` 是手写 indent-aware 解析器 (200+ 行)，刻意
不依赖 pyyaml 以保证 stdlib-only。当前实现不支持:

- 多行字符串 (`|`、`>`)
- 锚点 / 别名 (`&` / `*`)
- 流式与块式混合 (`{key: val, sub: [a, b]}` 嵌套)
- inline comment 在 list 元素后面

SCHEMA.md 是用户手编的——一旦用户写 `description: |\n  multi-line`
这种合法 YAML，解析器静默丢字段，下游 schema_validate 看到 missing
`description` 报奇怪错误。建议: 至少为不支持的语法明确报错，别静默忽略。

### 2.7 【🟠 MEDIUM】`external_plugin_run` 缺少几条易写的回归测试

`tests/run_smoke.py` Tests 8-10 覆盖了 metachar 拒绝和 preview 模式，但**没有**:

- prompt-injection 标记 `<|im_start|>` / "ignore previous" 真的被替换
  (`INJECTION_PATTERNS` 这一段没人测)
- `max_output_bytes` 截断的 truncated header 是否被写进 frontmatter
- 子进程 `_safe_env()` 真的不漏 `OPENAI_API_KEY` 之类敏感变量给 child

少一条某天会出事。

### 2.8 【🟡 LOW】`find_wiki_root` 9 步解析的优先级反直觉

第 3 步 (cwd 在某个 wiki root 内) 会**早于** 第 4 步 (`LLM_WIKI_PROJECT`
环境变量)。如果用户在 `~/.llm-wiki/necall/` 内显式
`export LLM_WIKI_PROJECT=rtc`，结果还是 necall。CLAUDE.md / AGENTS.md
都罗列了顺序，但没解释「为什么在 wiki 内的环境变量不能覆盖」。

### 2.9 【🟡 LOW】`plugin/CLAUDE.md` 与 `plugin/AGENTS.md` 内容 90% 重叠

一份在改、另一份在漂。建议提炼 `plugin/_OPS.md` 共享部分，两个壳文件 include。

### 2.10 【🟡 LOW】scripts 目录散落两份

- `scripts/build_skill_md.py` (repo root, dev-only)
- `plugin/scripts/*.py` (deterministic core)

`README.md` 安装段鼓励 `cp -r kata/plugin/scripts ./scripts`——这条命令
对 Codex CLI 用户**实际**不会包含 build_skill_md。OK 但要明示。

## 4. 一句话结论

**v1.7.2 在工程基本面上是扎实的** (deterministic 脚本 + JSON Schema +
smoke test + git hook + 多项目 resolver)，但**叙事层和承诺层落后于实现 1-2
个版本**: 三个核心文档同时教用户写已删除的 `command_template`、宣传 9 个
skill 而装了 12 个、watcher 守护进程在自家多项目卖点上崩。**优先解决
#1-#4 这四条就能把"可用度"和"诚实度"都拉齐。** v1.6 dogfood 是这套机器
最贵的 unfinished business，#5/#6 决定它接下来 4 周是否真的产生数据。
